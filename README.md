**Radmin VPN 第三方客户端** —— 高性能、高稳定的增强型控制工具。

> ⚠️ **免责声明**：本项目通过逆向分析实现了与 Radmin VPN 本地服务的互操作。
> 仅供**个人学习与自用**。Famatech 的 EULA 可能禁止此类行为，
> 使用存在**账号被封禁**的风险。请自行评估并承担后果。
> 本项目**不包含**任何破解、绕过授权或侵犯他人隐私的功能 ——
> 所有操作都限于**你自己账号下、你自己加入的网络**。

## 快速上手

```powershell
# 1. 编译
dotnet build src/RvpnKit.Client/RvpnKit.Client.csproj -c Release

# 2. 运行（需要 Radmin VPN 服务在运行）
src/RvpnKit.Client/bin/Release/net10.0/rvpnkit.exe
```

### 输出模式

| 命令 | 用途 |
|---|---|
| `rvpnkit` | 完整报告：网卡状态 / 对端列表 / 成员身份 / 活跃节点 |
| `rvpnkit --all` | 同上，但成员列表不截断（默认只显示前 30 行） |
| `rvpnkit --list` | 制表符分隔列表，便于 `Select-String`、`awk` 等处理（**无装饰**） |
| `rvpnkit --json` | JSON 输出，便于脚本或其它程序消费（**无装饰**） |
| `rvpnkit --monitor` | **实时监控**：成员上线 / 下线 / 节点活动 |
| `rvpnkit --no-color` | 关闭配色（也尊重 `NO_COLOR` 环境变量） |

> 装饰性的边框、艺术字、进度条**只作用于人类阅读的报告与监控**。
> `--json` / `--list` 的输出保持纯净，可直接被程序解析。

### 视觉层的实现要点

- **CJK 宽度对齐**：中文在终端占两格，表格按显示宽度而非字符数补空格，否则错位
- **颜色自适应**：输出被重定向到文件/管道时自动关闭颜色，并尊重 `NO_COLOR`
- **艺术字程序化拼接**：从等宽字形表拼出横幅 —— 手写 figlet 极易某行短几格，
  本项目就踩过（最后一个 `T` 被截断，导致行宽 55/52 不齐、框线参差）

## 数据来源

本客户端采用**多源聚合**：每个数据源都独立可验证，互为补充。

| 数据源 | 提供 | 可靠性 |
|---|---|---|
| **网卡邻居表** | 对端虚拟 IP + MAC + 可达状态 | ✅ 高（网卡驱动维护，数据面事实来源） |
| **服务日志** | 节点 ID + 别名 + 连接方式 + 时间 | ✅ 高（含精确时间戳） |
| **控制管道** | 状态快照 + 增量事件；用于关联 IP 与身份 | ✅ 读取可靠 |

### IP ↔ 别名 是怎么关联的

管道快照里每个节点同时带着虚拟 IP 和别名，但**容器层格式尚未完全解析**。
因此不走结构解析，而用三条实测规律做关联：

1. 虚拟 IP 以 **4 字节原始形式**出现（`26.169.61.178` → `1a a9 3d b2`）
2. 别名以 **UTF-16LE** 出现，起始偏移**可能是奇数**（这点极易漏掉）
3. 同一节点记录内，两者相距约 100~170 字节

单靠「邻近」会产生大量误配 —— 二进制块误解码出来的 CJK 串很像别名。
所以再加一道**白名单**：只有能在服务日志的已知别名里精确命中的文本才采用。
最后做双向去重，保证严格一对一。

> 稳定性验证方法：连续 3 次采集快照，统计共有 IP 的映射是否一致。
> 结果 250/250 全部一致 → 说明关联稳定，而非随机噪声。

## 原理

Radmin VPN 由三个部分组成，**控制面**与**数据面**是分开的：

```
RvRvpnGui.exe  (Qt5, x86, 用户态 UI)
      │  命名管道 \\.\pipe\RadminVpnGuiChannel  (自描述 TLV 记录流，只读)
      ▼
RvControlSvc.exe  (x86, SYSTEM 权限)  ←── 真正干活的实体
      ├── RvROLClient.dll   云端会话 / ENet 可靠 UDP / NAT 打洞 / 中继
      ├── RvNetMP60.sys     虚拟网卡驱动
      └── 虚拟 IP 段 26.0.0.0/8
      ▼
   radminte.com 后端池
      ├── ServerAddress   注册 / 信令服务器
      ├── ProxyServers     中继节点（流量中转）
      └── fail / upload 域
```

**核心设计决策：复用官方服务作为底层，本项目只做增强控制层。**

理由：

1. `RvControlSvc` 已经以 SYSTEM 权限持有**完成认证、注册、NAT 打洞**的云会话
2. 自己重写 ENet 可靠传输 + 打洞 + 加密体系是**数月工作量**，且必然不如原版稳定
3. 管道是**多客户端**的 —— 我们挂上去不影响官方 GUI 正常工作（实测确认）
4. 连接后服务会**主动推送完整状态快照**，之后是增量事件流，天然适合做实时监控

### 已踩过的关键坑

1. **管道 ACL 只授予读权限**：以 `GENERIC_READ | GENERIC_WRITE` 打开会被拒绝
   （Win32 错误 5）。必须**只读打开**。探测结果：只读 ✓ / 读写 ✗ / 只写 ✗。
2. **管道不能用重叠 I/O**：服务端实例是同步字节流模式，`FILE_FLAG_OVERLAPPED`
   会被拒。因此实现上用**同步句柄 + 专用读线程**。
3. **本机有 HIPS 安全软件**：`CreateRemoteThread` 注入虽然返回成功，但远程线程
   实际不执行（连 `GetCurrentProcessId` 都返回 0）。因此放弃了 hook 官方 GUI
   来抓命令格式的路线。

## 协议摘要

完整逆向笔记见 [`docs/PROTOCOL.md`](docs/PROTOCOL.md)。

### 帧边界
```
[frame_len : u32 LE][记录流…]
```

### 记录结构（字段号均为**大端**）

| 类型 | 结构 |
|---|---|
| `0x04` | `04 \| fid:u16 BE \| value:u32 LE` |
| `0x08` | `08 \| fid:u16 BE \| value:u64 LE` |
| `0x0B` | `0b \| fid:u16 BE \| value:u8` |
| `0x0C` | `0c \| fid:u16 BE \| value:u16 LE` |
| `0x03` | `03 \| fid:u16 BE \| len:u16 BE \| UTF-16LE(len 字节，以 U+0000 起头)` |
| `0x09`/`0x0D`/`0x10` | `.. \| fid:u16 BE \| 16 字节块（IPv4 或 GUID）` |

字符串记录的关键不变量：**`len == 2 × (字符数 + 1)`**，已用 5 组真实样本交叉验证。

### 已确认字段

| field id | 类型 | 语义 |
|---|---|---|
| `0x01c9` | str | 节点连接 IP |
| `0x01e1` | u64 | 节点 ID |
| `0x01e9` | str | 节点别名 / 主机名 |
| `0x01ed` | str | 客户端版本号 |
| `0x0304` | str | 网络名 |
| `0x0105` | blob16 | 节点虚拟 IP |
| `0x05d` `0x5e` `0x5f` | u32 | 超时 15000 / 60000 / 300000 ms |
| `0x0d6` | u32 | 帧序号（逐帧递增） |

### 已知难点

**1. 命令写路径未打通（主要缺口）。**

这是唯一没跨过的关卡，卡在**命令报文的精确编码**上。已知：

- 权限层面允许写：Python 侧连续 12 次「读写打开」全部成功，`WriteFile` 可用
- .NET 侧读写打开会得到 ERROR_ACCESS_DENIED（只读始终成功），原因未定位
- 但更根本的问题是：**不知道命令报文该长什么样**

服务对无法解析的报文**静默丢弃且不写日志**，而只有解析成功的请求才会记录
`[req:N] Succeeded`。于是形成死锁：

> 必须格式正确才能得到反馈，但不知道格式就无法构造正确报文。

已排除的获取途径：

| 途径 | 阻塞原因 |
|---|---|
| 注入官方 GUI 抓真实报文 | 本机 HIPS 拦截远程线程（返回成功但实际不执行） |
| UI 自动化代驱动 GUI | Qt5 未启用无障碍桥接，UIA 树为 0 元素 |
| 盲试报文字节 | 服务无任何错误反馈，6 个候选帧全部无响应 |
| 按字段号搜机器码立即数 | 字段号不以相邻字节写入，搜不到 |

**2. 容器层格式未完全对齐。**

字符串与标量记录已能稳定识别；嵌套容器的编码仍在收敛。
**但这已不影响功能** —— IP ↔ 别名 的关联改用「4 字节 IP 锚点 + UTF-16 别名 +
白名单校验 + 邻近配对」的思路绕过，实测 100% 稳定。

**3. 邻居表的实现取舍。**

直接 P/Invoke `GetIpNetTable2` 时，`MIB_IPNET_ROW2` 的内嵌 `SOCKADDR_INET`
导致结构体布局始终对不上（返回 0 条）。最终改用解析 `arp -a` 文本输出 ——
**可靠性优先**，代价是多一次进程启动开销。
