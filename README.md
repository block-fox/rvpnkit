## 数据来源

本客户端采用**多源聚合**：每个数据源都独立可验证，互为补充。

| 数据源 | 提供 | 可靠性 |
|---|---|---|
| **网卡邻居表** | 对端虚拟 IP + MAC + 可达状态 | ✅ 高（网卡驱动维护，数据面事实来源） |
| **服务日志** | 节点 ID + 别名 + 连接方式 + 时间 | ✅ 高（含精确时间戳） |
| **控制管道** | 完整状态快照 + 增量事件流 | ⚠️ 部分（见下方限制） |

## 原理

Radmin VPN 由三个部分组成，**控制面**与**数据面**是分开的：

```
RvRvpnGui.exe  (Qt5, x86, 用户态 UI)
      │  命名管道 \\.\pipe\RadminVpnGuiChannel  (自描述 TLV 记录流，只读)
      ▼
RvControlSvc.exe  (x86, SYSTEM 权限)  ←── 真正干活的实体
      ├── RvROLClient.dll   云端会话 / ENet 可靠 UDP / NAT 打洞 / 中继
      ├── RvNetMP60.sys     虚拟网卡驱动
      └── 虚拟 IP 段 26.0.0.0/8
      ▼
   radminte.com 后端池
      ├── ServerAddress   注册 / 信令服务器
      ├── ProxyServers     中继节点（流量中转）
      └── fail / upload 域
```

**核心设计决策：复用官方服务作为底层，本项目只做增强控制层。**

理由：

1. `RvControlSvc` 已经以 SYSTEM 权限持有**完成认证、注册、NAT 打洞**的云会话
2. 自己重写 ENet 可靠传输 + 打洞 + 加密体系是**数月工作量**，且必然不如原版稳定
3. 管道是**多客户端**的 —— 我们挂上去不影响官方 GUI 正常工作（实测确认）
4. 连接后服务会**主动推送完整状态快照**，之后是增量事件流，天然适合做实时监控

### 已踩过的关键坑

1. **管道 ACL 只授予读权限**：以 `GENERIC_READ | GENERIC_WRITE` 打开会被拒绝
   （Win32 错误 5）。必须**只读打开**。探测结果：只读 ✓ / 读写 ✗ / 只写 ✗。
2. **管道不能用重叠 I/O**：服务端实例是同步字节流模式，`FILE_FLAG_OVERLAPPED`
   会被拒。因此实现上用**同步句柄 + 专用读线程**。
3. **本机有 HIPS 安全软件**：`CreateRemoteThread` 注入虽然返回成功，但远程线程
   实际不执行（连 `GetCurrentProcessId` 都返回 0）。因此放弃了 hook 官方 GUI
   来抓命令格式的路线。

## 协议摘要

完整逆向笔记见 [`docs/PROTOCOL.md`](docs/PROTOCOL.md)。

### 帧边界
```
[frame_len : u32 LE][记录流…]
```

### 记录结构（字段号均为**大端**）

| 类型 | 结构 |
|---|---|
| `0x04` | `04 \| fid:u16 BE \| value:u32 LE` |
| `0x08` | `08 \| fid:u16 BE \| value:u64 LE` |
| `0x0B` | `0b \| fid:u16 BE \| value:u8` |
| `0x0C` | `0c \| fid:u16 BE \| value:u16 LE` |
| `0x03` | `03 \| fid:u16 BE \| len:u16 BE \| UTF-16LE(len 字节，以 U+0000 起头)` |
| `0x09`/`0x0D`/`0x10` | `.. \| fid:u16 BE \| 16 字节块（IPv4 或 GUID）` |

字符串记录的关键不变量：**`len == 2 × (字符数 + 1)`**，已用 5 组真实样本交叉验证。

### 已确认字段

| field id | 类型 | 语义 |
|---|---|---|
| `0x01c9` | str | 节点连接 IP |
| `0x01e1` | u64 | 节点 ID |
| `0x01e9` | str | 节点别名 / 主机名 |
| `0x01ed` | str | 客户端版本号 |
| `0x0304` | str | 网络名 |
| `0x0105` | blob16 | 节点虚拟 IP |
| `0x05d` `0x5e` `0x5f` | u32 | 超时 15000 / 60000 / 300000 ms |
| `0x0d6` | u32 | 帧序号（逐帧递增） |

## 构建

### 前置

- **.NET 10 SDK**（本仓库用 `10.0.402` 验证）
- 可选：**Zig**（只在需要重新编译 `native/` 下的 C 代码时需要）

### 编译与运行

```powershell
dotnet build src/RvpnKit.Client/RvpnKit.Client.csproj -c Release
src/RvpnKit.Client/bin/Release/net10.0/rvpnkit.exe
```

### 协议调试工具

```powershell
# 回放抓包，验证协议解码器
rvpn verify <capture.bin>

# 用已验证的线格式解析抓包，输出同步率与字段语义
rvpn decode <capture.bin>

# 穷举求解线格式语法
rvpn solve <capture.bin>
```

> `recon/` 与 `captures/` 目录**已被 .gitignore 排除** ——
> 管道抓包含有你网络里真实成员的 IP、主机名等信息，绝不应提交到仓库。

### 编译注入器（可选，当前路线未使用）

```powershell
zig cc -target x86-windows-gnu -shared -O2 -o native/rvpipe_hook32.dll native/rvpipe_hook.c
```

### 已验证的能力边界

**可以做到（普通用户权限）：**

- 读取控制管道的完整状态流（快照 + 增量事件）
- 读取网卡邻居表：对端虚拟 IP、MAC、可达状态
- 解析服务日志：节点 ID、别名、连接方式、精确时间
- 只读监控，不影响官方 GUI 正常运行

**做不到（需管理员权限）：**

- 启用/禁用虚拟网卡 —— `Disable-NetAdapter` 返回 Access denied

### 已知难点

**1. 命令写路径未打通（主要缺口）。**

权限层面是允许的：Python 侧连续 12 次「读写打开」全部成功。
但从 **.NET 进程**发起读写打开会得到 ERROR_ACCESS_DENIED，只读打开则始终成功 ——
原因尚未定位，推测与 .NET 请求的附加访问位有关。

> **修正记录**：早期曾误判为「管道 ACL 只授予读权限」。后续用「逐例隔离 + 重试」
> 重新测试后推翻了该结论 —— 当时的 ERROR_ACCESS_DENIED 是连续探测时句柄竞争
> 造成的假象。客户端现在采用**降级策略**：先试读写，失败退回只读，永不崩溃。

**2. 容器层格式未完全对齐。**

字符串与标量记录已能稳定识别；嵌套容器的编码仍在收敛，当前同步率约 45%。
这不影响已实现的功能，因为成员 IP 来自网卡邻居表、节点身份来自服务日志 ——
都不依赖管道容器解析。

**3. UI 自动化路线不可用。**

官方 GUI 是 Qt5 应用，未启用无障碍桥接，即使设置 `QT_ACCESSIBILITY=1` 重启后，
UI Automation 树仍为空（0 个元素）。因此无法通过 UI 自动化代驱动 GUI。

**4. 邻居表的实现取舍。**

直接 P/Invoke `GetIpNetTable2` 时，`MIB_IPNET_ROW2` 的内嵌 `SOCKADDR_INET`
导致结构体布局始终对不上（返回 0 条）。最终改用解析 `arp -a` 文本输出 ——
**可靠性优先**，代价是多一次进程启动开销。

### 后续可选路线

1. **定位 .NET 读写打开失败的原因** —— 最直接，成功后即可构造并下发命令
2. **从 Python 侧实现写路径** —— Python 的读写打开已验证可用，可先用 Python
   原型验证命令格式，再移植回 .NET
3. **提权后 hook `RvControlSvc`** —— 最彻底，但需要管理员权限
4. **直接调用 `RvROLClient.dll` 导出函数** —— 需自实现宿主与回调
